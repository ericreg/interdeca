# paper_synth — reproducing the synthetic-dataset results and figures (manuscript Figures 6–13)

Analyses and figures for the *Synthetic Texture Dataset* Methods/Results section of
`Coloring paper draft.docx`. The text edits and figure numbering are in
`SYNTHETIC_SECTION_EDITS.md`; every number there is traced to a file in `results/`.

```
input data  ->  build_cache.py  ->  experiments e*.py  ->  results/*.json|npz  ->  fig*.py  ->  figures/*.png|pdf
 (~14 GB)         (~1 min)          (~20–40 min, see 4b)                          (~25 s)
```

`results/` and `figures/` are committed, so there are two levels of reproduction:

- **Redraw only** (section 5): rebuilds the figures from the committed `results/`. Checks the
  plotting code, not the numbers.
- **Full reproduction** (sections 1–6): recomputes every number from the input data and compares
  it with the committed `results/`. This is the real check.

## 3. Input data

The pipeline reads three input folders. Point one env var at each, wherever they live on your
machine, and keep these exports in every shell you run the pipeline from (without them the code
falls back to the original machine's `/mnt/data/...` paths):

```bash
export SYNTH_SRC=/path/to/cichlid-synth-decimated
export SYNTH_MODULE_RUN=/path/to/2026_07-16_20_37_11        # the ColorAtlas run folder
export SYNTH_DONOR_SCANS=/path/to/3D_Fish                    # original donor scans
```

Each folder must contain at least the following (other files are ignored):

```
$SYNTH_SRC/                           synthetic dataset (pre-module), 1.6 GB
├── samples.csv                       ground truth: generating parameters per sample
├── images/<sample>.png               250 synthetic 2048² textures (native UV)
├── meshes/<sample>.obj               250 donor-mesh copies
└── landmarks/<sample>.mrk.json       250 × 47 landmarks (Slicer markups)

$SYNTH_MODULE_RUN/                    ColorAtlas output (post-module), 11.4 GB used
├── colorAnalysis/
│   ├── atlasModelUV.obj              mean-shape atlas (24,999 v / 49,997 f)
│   ├── atlasLM.mrk.json              atlas landmarks
│   ├── atlasTextures/*.png           250 atlas-space textures (+ average_texture.png, ignored)
│   └── resampledOBJ_withUV/*_resampled.obj   per-specimen meshes on atlas topology (e1 only)
└── ATLAS/alignedModels/*_align.obj           per-specimen aligned source meshes (e1 only)

$SYNTH_DONOR_SCANS/                   original donor scans, Figure 6 only, 0.2 GB
├── Texture/<donor>.png               8 files
└── Downsampled_decimate/Models/<donor>.obj   7 files
```

Quick check that everything is where the code expects it:

```bash
for p in "$SYNTH_SRC"/{samples.csv,images,meshes,landmarks} \
         "$SYNTH_MODULE_RUN"/colorAnalysis/{atlasModelUV.obj,atlasLM.mrk.json,atlasTextures,resampledOBJ_withUV} \
         "$SYNTH_MODULE_RUN"/ATLAS/alignedModels \
         "$SYNTH_DONOR_SCANS"/{Texture,Downsampled_decimate/Models}; do
  [ -e "$p" ] && echo "ok       $p" || echo "MISSING  $p"
done
```

### Where the inputs came from (not part of the reproduction)

1. `cichlid-synth-decimated/` was generated by `color_fishy_tps.py` at the repo root (seven
   decimated donor scans, 250 samples). See the repo docs on synthetic dataset generation.
2. The module run is the ColorAtlas Slicer module's output for those 250 specimens (merge

## 4. Full reproduction

### 4a. Keep the committed outputs as the reference

The rerun overwrites `results/` and `figures/`, so snapshot them first:

```bash
cp -r results results_ref
cp -r figures figures_ref
rm -rf cache                 # start from no cached intermediates
```

### 4b. Run

Run the commands in this order. Lines joined with `&&` depend on each other. The separate
groups are independent and may run in parallel in separate shells (each needs the exports
from section 3).

**Thread settings matter.** Several experiments fit high-dimensional logistic models, whose
result depends slightly on how many BLAS threads compute it. The committed results came from
the per-script settings below, so **do not export `OMP_NUM_THREADS` globally**. e4 and e5b get
an explicit 4-thread prefix. e2 and e6 set their own default (2 and 4). The rest run with the
library default.

```bash
T4="env OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4 MKL_NUM_THREADS=4 NUMEXPR_NUM_THREADS=4"

$PY build_cache.py                                                   # run first

$PY e1_fidelity.py && $PY e1b_correspondence.py                      # Figs 7, 8
$PY e2_preservation.py && $PY e2b_donorblocked.py                    # Fig 9
$PY e3_module_eda.py                                                 # Fig 10
$T4 $PY e4_byoa_descriptors.py                                       # Fig 11
$T4 $PY e5b_expert_repr.py                                           # Fig 12
$PY e6b_limits.py                                                    # Fig 13

# only after all of the above:
$PY e2c_landmark_baseline.py         # needs e1b + e2 outputs           # Fig 9
$PY e6_negative_results.py           # needs e1 outputs                 # Fig 13
```

Avoid running many default-thread scripts at once on a many-core machine. Each one starts a
thread per core, they oversubscribe the CPU, and small problems get dramatically slower: e2b
took 32 min under contention versus 10 s with 4 threads. If speed matters more than an exact
match, you can run e2b and e2c with `$T4` as well. That changes a few shuffled-label null values in
the 3,600-feature `post_spatial_flat` / `lm_flat` rows by ≤ 0.006 and no number quoted in the
paper (verified).

The dependencies: e2b and e2c read `results/e2_preservation_arrays.npz`, e2c reads
`results/e1b_correspondence.json`, and e6 reads `results/e1_fidelity*`. If e6 can't find those
files it skips that sub-analysis rather than failing.

Runtimes measured on the original 32-core machine (2026-10-05), with several scripts running at
once. Expect them to vary with core count and load.

### 4c. Compare with the reference

```bash
$PY compare_results.py            # results/ vs results_ref/, figures/ vs figures_ref/
$PY compare_results.py -v         # also list every differing value
```

Every numeric value in every JSON and every array in every `.npz` is compared (wall-clock fields
are ignored), and figures are compared pixel by pixel. Each file is reported as `IDENTICAL`,
`CLOSE` (relative difference ≤ 1e-6, i.e. floating-point noise) or `DIFFERS`. The exit status is 0
only if nothing is outside tolerance.

How to interpret the outcome: see section 6.

## 6. What to expect from the comparison

The committed `results/` and `figures/` **are** the output of a clean run (empty `cache/`) that
followed section 4b exactly, on the original machine on 2026-10-05. On that machine, every script
checked was deterministic: rerunning it on identical inputs reproduced its output exactly. That
was checked for e1–e3, e5b (three times) and e6. A second full clean run was not done.

On a different machine (other CPU, core count or BLAS build), floating-point results differ in the
last bits. For most of the pipeline that doesn't matter, but three groups of values are
**numerically chaotic**: a change of ~1e-9 in their inputs moves them in the 2nd decimal.

| Values | Why | Seen moving by |
|---|---|---|
| e5b `display_silhouette.*` (2-D UMAP display, Figure 12E) and `emb_*` | UMAP layout | 0.02 (the quoted 160-tag value was 0.237 vs 0.252 for a 2e-9 change in the eigenbasis) |
| e6 `item2_ica.*` single-component AUCs (`best_comp_auc_ica`, `single_auc_ica_minus_pca`, `best_single_auc_ica_gain`) | FastICA rotation | 0.1 |
| e4 / e2 / e2b / e2c rows for the 3,600-feature `D2_spatial_flatten`, `post_spatial_flat`, `lm_flat` | high-dimensional logistic fits | ≤ 0.006 |
| e5b `pairwise_warp.stripe.10` | metric-learning fit at 10 pairs (chance level) | 0.02 |

Expect these to show as DIFFERS in `compare_results.py`, and Figures 11–12 to differ by about 1% of
pixels. Everything else should be IDENTICAL or CLOSE. Everything quoted in the paper is stable
except **one** value: the Figure 12E silhouette at 160 tags (currently +0.252, quoted as +0.25),
which can print as +0.24 or +0.25. The e6 ICA claims that are quoted (subspace angle
< 3 × 10⁻¹² degrees, accuracies within 0.003) hold in every run so far.

So the bar for "reproduced" on another machine is: `compare_results.py -v` shows differences
only in the rows above, and no number quoted in the paper changes at its printed precision
(the 160-tag silhouette excepted, ±0.02).

Things that make the comparison fail outright:
- **Exporting a single global thread count.** e2, e2b and e2c shift slightly, and e4 / e5b / e6
  shift if it isn't 4.
- **Package versions other than `requirements-paper.txt`.** Not tested; treat any difference
  as suspect.

History: before 2026-10-05, `fishpipe.spectral.laplacian_eigenbasis` returned eigenvectors with
arbitrary signs, so every fresh build of the spectral descriptors differed. It now fixes each
eigenvector's sign deterministically, and the results were regenerated from a clean run. Compared
with the August results, the only quoted number that changed is that silhouette (+0.24 → +0.25).
