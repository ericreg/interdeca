Atlas and MorphoWeave: CPU and memory baseline

The additional MorphoWeave runtime is predominantly repeated OBJ parsing and formatting in the adapter path. Both backends have a separate, larger memory problem: validation of an 8192 × 8192 source texture keeps about 6 GiB of floating-point texture buffers alive at once.

Ten successful fresh-process runs covered both backends. The same backend produced identical SHA-256 hashes for 33 exported files and presentation arrays across all five of its runs. These checks establish that profiling preserved the measured outputs; they do not establish equivalence between the two numerical backends. No numerical implementation, upstream source, or execution strategy was changed.

The adapter's MorphoWeave._inputs writes all three source meshes once for mean construction and again for final alignment. Upstream loads the reference mesh, reads and writes meshes for pre-alignment, imports the aligned population for its mean, then reads and writes meshes during final alignment. The adapter reads those final outputs back into internal records. Including common inspection and export, this becomes 16 reads and 19 writes, compared with native's 3 and 7.

The two upstream runAlign calls took 23.10 s inclusively; runMean took 6.01 s. Those totals contain the same file handling already counted above, so they must not be added to it. Inside runMean, denseCorrespondence took only 0.30 s for this dataset. This evidence supports preserving the upstream algorithms while reducing serialization around them.

Thread-aware Yappi CPU captures independently identify the OBJ parsing/formatting call stacks: native atlas CPU table and MorphoWeave atlas CPU table. Profiling every Python call inflated whole-process runtime to 246 s and 767 s respectively; those durations are excluded from the performance comparison. Per-pipeline .pstats and readable tables are archived alongside these files.

2. Memory: texture validation dominates the small dataset

Each panel has its own time range and the same memory scale. Dashed lines mark the end of atlas/texture processing and color processing. Green measures only arrays reachable from the manager's task-result table; it resets when that table is released. It excludes application-owned results, VTK objects, active-operation temporaries, and allocator retention.

The source textures are 8192 × 8192 RGBA PNG, 8192 × 8192 RGBA TIFF, and 4096 × 4096 RGBA PNG. A single 8192² RGBA image in float64 occupies 8192 × 8192 × 4 × 8 = 2 GiB. The 512 × 512 bake setting affects output textures; it does not reduce these source-image validation allocations.

Memray's tracked live-allocation peak was 7,130.7 MiB for native and 7,109.3 MiB for MorphoWeave, approximately 6.96 and 6.94 GiB. Both peaks occurred in the same pre-bake source-texture read, with these buffers simultaneously alive:

The three floating-point representations alone total 6 GiB, about 86% of the tracked live peak. Blender.bake_specimen_texture calls TextureIO.read to validate the original texture before passing its path to Blender. Inspection also performs full source-texture validation earlier. These transient allocations recur; they do not mean all source textures are cached simultaneously.

Inspect the call chains in the native allocation flame graph and MorphoWeave allocation flame graph. Baseline RSS exceeds the tracked heap peak because these are different runs and metrics: RSS includes imports, interpreter and library memory, allocator-retained pages, and other resident mappings. Changes in resident pages alone do not prove a memory leak.

Across the entire timer pass, Arrays.frozen returned copies totalling 19.49 GiB for native and 21.12 GiB for MorphoWeave. This is cumulative copy traffic, not live memory. The 331/267 MiB manager-retained-array figures describe another distinct quantity: population geometry and completed task arrays kept until the pipeline returns.

3. What this implies for fifty specimens

No fifty-specimen or full-clams run was performed. The current implementation is not a streaming population pipeline in either backend: both inspect and retain the source meshes, and the serial manager keeps completed task results until the pipeline finishes. Native also retains mean contributions. Upstream MorphoWeave's importPaired builds a group containing all meshes, and runMean constructs a correspondence group before averaging.

The three source meshes require 91.7 MiB for raw vertex, triangle-index, and per-corner UV arrays (per-specimen dimensions and array sizes). Fifty meshes of the same average density would require approximately 1.49 GiB for those arrays alone, before aligned copies, correspondence, VTK, temporary arrays, Python objects, or textures. This is an illustrative geometry-size calculation, not a forecast of peak RSS.

Population geometry grows with specimen count. The large transient source-texture allocation depends mainly on the largest image dimensions and how many images are processed simultaneously. Multiplying the entire three-clam memory peak by 50/3 would therefore be misleading. Caching every decoded texture or every serialized mesh copy would add memory without addressing the ownership problem.

A bounded adapter cache can reduce duplicate transfers, but cannot by itself make upstream runMean stream one specimen at a time. Its bulk population contract must remain explicit in any memory budget.

4. Recommended next changes, not implemented here

  1. Reduce OBJ round trips at the host boundary. Investigate reusing already validated meshes and staged files between mean construction and alignment, while continuing to call upstream workflows. Bound the cache by bytes, release stage-local objects promptly, and retain disk-backed fallback. Preserve vertex/triangle order, per-corner UVs, coordinate transforms, and upstream cleanup behavior.
  2. Reduce full-resolution texture validation copies. Separate path/encoding validation from numerical pixel consumption where appropriate, and avoid repeatedly copying an already validated array. Preserve accepted input validation, sRGB/alpha semantics, and numerical output.
  3. Measure again after each change. Repeat baseline, timer, and allocation passes and check the same output fingerprints. Only after this should a separately approved larger dataset establish population memory growth.

These priorities address two distinct measured costs: adapter serialization is the strongest MorphoWeave CPU opportunity, while shared texture handling is the strongest small-dataset memory opportunity. A faster IPC transport would not remove the OBJ conversions measured inside this single application process.

The default harness makes ten sequential fresh-process runs: two baselines, one nested-timer pass, one CPU pass, and one allocation pass per backend. This recorded experiment completed the timer passes last. No cold filesystem-cache assumption is made.

  • Process-tree RSS and CPU were sampled every 100 ms. Brief peaks can be missed, and summing process RSS can double-count shared pages. The OS process high-water RSS is also archived in each rusage.json.
  • Private memory (USS) was unavailable for these processes on this Mac and remains null. It was not substituted with RSS or zero.
  • Yappi tables combine Python thread contexts; OS application CPU includes native-library threads. Blender CPU is recorded separately. Nested inclusive times overlap; exclusive timer spans subtract only other instrumented spans.
  • Memray begins after imports and measures the application process. Executed Blender processes are measured by external sampling, not Memray. Aggregated captures preserve allocations live at the peak, not total churn or a full allocation timeline.
  • Memray warned that interpreter debug symbols were unavailable on this Mac. Allocation sizes and Python call chains are available; detailed native C/C++ symbol attribution is incomplete.
  • An initial cProfile/custom-thread-clock attempt produced invalid negative timings and was rejected, including an interrupted companion run. Both were replaced with successful Yappi captures. They are excluded from all ten-run summaries and comparisons.
